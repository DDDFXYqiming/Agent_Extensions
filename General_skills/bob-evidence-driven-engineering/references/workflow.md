# 工作流程与角色交接

## 从需求到可执行验收

将用户要求变成小而可验收的切片，每个切片保留原要求编号、示例、边界、错误行为、明确排除项。对已有应用先保留兼容条件。条件可推断时记录假设并推进；会改变用户目的的选择才需要澄清。此前已确认的事项不重复询问。

spec 阶段的交付是 `docs/bob/spec.md`、`docs/bob/acceptance.feature`、`docs/bob/qa-plan.md`，纳入版本管理与源码指纹。Gherkin 的 Then 必须对应可观察断言（真实 DOM 变化、输出内容、退出码），不能只是"点击过按钮、请求没有抛异常"。每条验收都有正常、边界、异常三类中适用的案例。简单任务不必制造整套目录，已有规格可直接引用。

QA 计划从用户入口描述操作、前置条件、预期结果与恢复步骤。Web 应用检查真实 DOM 与显示结果；CLI 检查输入、输出和退出码；库代码检查公开接口。涉及视觉效果的验收由浏览器截图、图像比对或有视觉能力的主模型完成，文本证据只作补充。

规格交用户审阅，`approve` 记录指纹后才算合同生效。此后改动规格必须重新审阅，否则裁决报 `spec stale`。

## 保持上下文与责任清楚

有子代理能力时，各角色使用短交接材料（`bobflow.py checkpoint` 生成）；并行工作只分配相互独立的切片。需要隔离写入时由宿主建立 worktree，遵循已有分支和合并约定。

无子代理能力时按相同职责顺序执行，但每个阶段收尾仍要 `checkpoint`：相当于让"上一个角色"死亡、下一个角色从干净上下文加交接记录重新出生。这解决长会话的上下文污染与 lost-in-the-middle 问题，会话中断后任何 agent 读 `.bob/` 即可接续。

交接记录至少含源码指纹、覆盖需求编号、检查命令与退出码、报告路径、已知问题、期望接收方关注点。接收方不必把每条已验证断言重跑；但指纹变化后旧记录只作历史参考。脚本不启动任何生成模型，生成能力由宿主提供。

## 六个角色的职责

| 角色 | 职责 | 关键产出 |
| --- | --- | --- |
| spec | 切片需求、写可执行合同 | spec.md / acceptance.feature / qa-plan.md |
| code | 最小完整实现，保持测试可独立执行 | 通过 test 检查的代码 |
| clean | 按复杂度、逐函数覆盖、CRAP、重复代码证据重构；行为保持需前后测试支持 | 通过 crap/coverage 检查 |
| architect | 跨模块责任、依赖环、外部接口、数据所有权、部署边界；静态依赖规则优先 | 架构规则检查结果 |
| harden | 实际跑变异测试，消灭幸存变异 | 通过 mutation 检查 |
| qa | 把 QA 计划变成可执行脚本并重跑 | 可复用验收脚本 + 通过记录 |

注意：角色是职责划分，不是每次必须唤醒六个昂贵模型。风险低、有代表性数据验证过的流程可以合并阶段；建立基线或陌生领域则逐角色走全。

clean 的证据用法：不能用全项目平均覆盖率给单个函数的 CRAP 开脱；过长单职责分支也不自动等于要拆成一堆只收布尔参数的小函数。只在证据显示维护风险时重构。

harden 的证据用法：对幸存变异，先列可能原因与需优先查看的测试区域，再逐个处置。"可能是等价变异"只是调查线索，等价性需要逻辑证明或反例搜索并明确记录。工具报错、超时、未覆盖不能计作已杀死。优先增量变异只跑改动函数及其依赖，全量/抽样范围必须写进报告。

qa 的收尾：发现的问题交回最合适的角色修正，变更后重新运行受影响检查。对 Web 系统以真实用户入口为准，直接调后端接口只能补充证据。

## 固定流程与按需复核

默认保留所有明确要求的确定性检查。主模型的广泛复核有两种配置：

| 配置 | 主模型工作 | 用途 |
| --- | --- | --- |
| fixed | 每个职责均独立复核 | 建立基线、风险高或未校准的新领域 |
| assisted | 按证据聚焦异常和不确定项，保留抽样复核 | 已验证过的低风险流程 |

固定质量检查不能因为"上次没报错"而取消。与输入无关的空阶段可标不适用，写进配置与交付说明。连续同一失败且环境、代码与证据未变时，停止原样重试，收集新证据或改变方案；服务失败按显式重试预算处理。
