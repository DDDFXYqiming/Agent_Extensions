# 证据驱动开发流程

这套流程来自 Bob 的做法。人负责写需求，代码好不好由机器检查说了算，能不能交付由一个独立的 QA 子代理签字。整个流程由 `tools/bobflow.py` 一个脚本执行，脚本只用 Python 标准库，`init` 时复制进项目仓库。每一步的对错由命令退出码判定，文档里的要求没做到，对应命令会直接失败。

一句话记住分工。实现的负责写，机器负责判质量，独立 QA 负责放行。写代码的不能给自己发通行证。

## 退出码

| 退出码 | 含义 | 一般原因 |
| --- | --- | --- |
| 0 | 通过 | 这一步完成，可以继续 |
| 2 | 缺前置 | 没有规格、没有独立 QA 签字、或者没有新的检查结果 |
| 3 | 检查未通过 | 测试失败，覆盖率或复杂度不达标 |
| 4 | 需要人工批准 | 测试变少、跳过变多、门槛被调低这类改动需要书面说明 |

## 执行步骤

1. 首次使用运行 `python tools/bobflow.py init`。脚本探测项目的语言和测试工具，生成 `.bob/config.json`，把自身复制到 `tools/`，再装上 git 钩子。结束时打印检查清单，写明哪些检查已启用。
2. 运行 `python tools/bobflow.py spec`，在 `docs/bob/` 生成三份文件。`spec.md` 记录需求切片，`acceptance.feature` 记录验收场景，`qa-plan.md` 记录测试计划。
3. 填写三份文件。每个需求切片包含编号、示例、边界、错误行为、明确不做的部分。验收场景的每一步都要能观察到结果，例如页面上出现什么、命令输出什么、退出码是多少。
4. 运行 `python tools/bobflow.py approve` 记录规格意图。用户在线就请他过目再按。用户不在在线可以由你代签，脚本会标注成 `agent-unsigned`，流程继续往下走，不断流。这一道只确认"规格是不是要的东西"，不负责判质量。
5. 写代码。随时运行 `python tools/bobflow.py next` 查看当前进度和下一步命令。
6. 写完运行 `python tools/bobflow.py verify`。脚本跑测试、覆盖率等检查，把原始日志存进 `.bob/evidence/`。这一步会因为还没有独立 QA 签字而返回 `BLOCKED: 缺独立 QA 签字`，这是对的，接着做下一步。
7. **开一个独立 QA 子代理做最终验收并签字**，详见下一节。QA 子代理独立核对完会用 `qa-sign` 签发。
8. 再跑一次 `python tools/bobflow.py verify`（或 `decide`）。这次有独立 QA 签字，拿到 `PASS` 和 `.bob/decision.json`。
9. 运行 `python tools/bobflow.py checkpoint <阶段>` 保存交接记录，补齐标注待补的两节。阶段名用 spec、code、clean、architect、harden、qa 里的一个。
10. git commit 和 git push。钩子在提交和推送时重新运行检查，不通过就不让提交。

小改动（见下面判据）可以只做 1、2、5、6、7、8，规格只写一份填实的 `spec.md`（跳过 acceptance.feature 和 qa-plan.md），`approve` 时加 `--profile commit` 声明轻量，但独立 QA 签字一步不能省。

## 独立 QA 与子代理

放行权在独立 QA 手里，不在写代码的手里。做法是开一个干净上下文的子代理扮演 QA，让它看不到你的实现思路，只凭规格和公开入口去验。

**给 QA 子代理这些，不给别的：**

- 规格三件套（`docs/bob/spec.md`、`acceptance.feature`、`qa-plan.md`）。
- 项目的公开入口，怎么装、怎么跑、界面或命令行长什么样。
- 一条指令，按验收场景逐条从用户入口核对，跑 `python tools/bobflow.py verify`，通过后用 `python tools/bobflow.py qa-sign --role qa-subagent --by <你的名字>签发。

**不要给它：** 你写的实现代码、你的判断、你认为哪里可能有问题。它得自己从入口走一遍才算独立。

**各 harness 怎么开子代理：**

- 有子代理能力就直接开。pi 用 spawn 起子代理，codex 用 subagent 或 task，claude code 用 Task 工具。给它上面那份 QA 任务就行。
- 没有子代理能力，就用 CLI 调自己开一个新进程，比如 `pi -p --no-session "<QA 任务>"`，或者新开一个干净会话把 QA 任务发过去。关键是要有干净上下文。
- 都做不到，才在本会话里先放下实现思路、只拿规格重走一遍验收，然后 `python tools/bobflow.py qa-sign --role self` 降级自签。脚本会标注这是降级自验、不是独立 QA，有条件时要补一个真正的独立 QA。

`qa-sign` 只在当前代码有一次通过的检查结果时才放行，代码一变签字就过期。它防的就是同一个 agent 写完自己说自己好。独立 QA 签字是这套流程唯一的放行门，代替了"人必须签字"，把人从流程里解放出来。

## 什么算小改动

判断走全量还是轻量，看任务本身，不看催不催。下面几条都满足才算小改动。

- 改动限于一个函数或一个文件的局部，不超过约三十行。
- 不新增对外接口，不改数据格式，不影响别的模块。
- 测试可以只补一两个针对这次改动的用例，不需要成套的验收场景。
- 修一个已有测试已经指出来的明确 bug。

只要出现新功能、跨文件、要设计接口、或者你不确定算不算小，就走完整十步。拿不准时宁可走全量，多花的时间比交付翻车便宜。

## 命令返回非 0 时怎么做

| 输出开头 | 原因 | 做法 |
| --- | --- | --- |
| `BLOCKED: missing spec` | 三份规格文件不全 | 回到步骤 2 |
| `BLOCKED: 规格未确认` | 规格没有意图确认 | 运行 approve，在线请用户过目，不在就代签标注 |
| `BLOCKED: spec stale` | 规格改过后没重新确认 | 重新 approve |
| `BLOCKED: 缺独立 QA 签字` | 没人放行 | 开子代理做独立 QA，用 qa-sign 签发 |
| `BLOCKED: QA 签字过期` | QA 签完代码又改了 | 重跑独立 QA，重新 qa-sign |
| `BLOCKED: evidence missing/stale` | 没检查结果，或代码改过没重新检查 | 运行 verify |
| `BLOCKED: source changed during checks` | 检查过程中改了产品代码 | 把这部分改动单独提交，重新 verify |
| `FAIL:` | 检查真失败了 | 修代码或补测试，重新 verify |
| `WAIVER:` | 触发了防刷绿检查 | 填写 `docs/bob/waivers/` 里生成的说明文件，用户批准后把文件名改成 `APPROVED-` 开头，重新 verify |

## 写规格的要求

规格是人和 QA 共同的依据，质量要求都落在这里。

- 验收场景的"那么"一步写可观察结果。禁止写"点击后没有报错"这种验收。
- 每条验收至少覆盖正常、边界、错误三种里适用的情况。
- 写清不做什么。范围外的改动不进这一轮。
- 已有项目先写清必须保持不变的接口和行为。

## 禁止的行为

做了这些事，交付会被工具拒绝或者失去意义。

- 写代码的给自己放行。放行必须是独立 QA 子代理的 qa-sign，不能用 --role self 冒充独立。
- 删测试、给测试加跳过标记、降低门槛、缩小检查范围，用这些办法让检查变绿。
- 汇报"已完成"而不贴 decision.json 的结果。完成与否以它为准。
- 用旧检查记录冒充当前结果。代码改过，记录就作废。
- 检查过程中顺手改产品代码。这轮报告直接作废。
- 幸存变异标成"等价"就跳过。等价需要书面的逻辑证明或反例搜索记录。
- 门槛改动不写理由。所有门槛调整都要走 `docs/bob/waivers/` 的书面说明和用户批准。

## 六个阶段

spec 写规格，code 写实现，clean 处理复杂度和重复代码，architect 管跨模块的依赖和边界，harden 跑变异测试补测试，qa 从真实入口做独立验收。小任务可以合并阶段，每个阶段结束都要 checkpoint，下个阶段从交接记录接续。qa 这一阶段的独立性最关键，尽量交给独立子代理。各阶段的详细规程见 `references/workflow.md`，指标口径和报告格式见 `references/quality.md`。

## 已知限制

独立 QA 签字防的是"实现者自卖自夸"，靠的是上下文隔离加确定性工具，不是密码学签名。同一个 agent 仍然可能假装开子代理然后自己 qa-sign，这套机制拦不住蓄意造假。git 钩子可以用 `--no-verify` 跳过，完全绕过本流程的改动也拦不住。有远程仓库的项目建议开分支保护，把检查设成合并前必过。剩下的靠对账发现，也就是拿 decision.json 的时间和指纹跟实际提交核对。
